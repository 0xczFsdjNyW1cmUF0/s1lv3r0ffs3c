# ret2libc: первая ROP-цепочка, которая собралась

**Машина:** [ret2libc](https://tryhackme.com/room/ret2libc) (medium, pwn, Linux)
**Инструменты:** gdb + gef (или pwntools), Ghidra, checksec.

## Разбор бинаря

`exploit_me` спрашивает имя и печатает его. 30 символов `A` — segfault, переполнение есть. checksec:

- NX — включён (шеллкод на стеке не исполнится)
- canary — нет
- RELRO — partial
- в коде есть `setuid(0)`

Значит, код исполнять через стек не выйдет, но перезаписать return address и собрать ROP-цепочку из уже загруженного libc — самое то. Ghidra показывает виновника: `gets()` в буфер на 10 байт, без всякой проверки длины.

## Оффсет

В gdb через gef:

```
pattern create 100
run   # вставляем паттерн
pattern search $rsp
```

Получаем точное смещение до instruction pointer. (pwntools-вариант — `cyclic` + `cyclic_find`, на третий раз перешёл на него, быстрее.)

## Цепочка

Идея ret2libc: в libc лежит всё нужное, включая строку `/bin/sh`. Собираем из гаджетов программы:

```
[padding до return address]
[pop rdi; ret]      ← гаджет, кладёт аргумент в rdi
[адрес "/bin/sh"]
[адрес system]      ← вызов system("/bin/sh")
```

`pop rdi; ret` ищется `ROPgadget`-ом или `ropper`-ом по бинарю. Адреса `system` и строки `/bin/sh` в libc берутся из отладки (gdb: `p system`, `search-pattern /bin/sh`). Бинарь вызывает `setuid(0)` до чтения ввода — значит, шелл из `system()` прилетает сразу root'овый.

Оформляется всё скриптом на pwntools: `padding + p64(pop_rdi) + p64(binsh) + p64(system)` — запуск, шелл, флаг.

## Заметка

Первая самостоятельно собранная ROP-цепочка — как первый самостоятельный разбор двигателя: медленно, но потом перестаёшь бояться. Главное, что уложилось: NX не останавливает атаку, а только переносит её из «писать код» в «собирать программу из чужих кусков».
