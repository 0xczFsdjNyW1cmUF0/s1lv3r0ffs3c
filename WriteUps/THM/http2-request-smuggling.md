# HTTP/2 Request Smuggling: десинк через даунгрейд

**Машина:** [HTTP/2 Request Smuggling](https://tryhackme.com/room/http2requestsmuggling) (hard, web)
**Суть:** HTTP/2 сам по себе защищает от смагглинга (длины полей заданы явно), но на границе фронт (H2) → бэкенд (H1) защита исчезает.

## Почему HTTP/1 смагглинится

В HTTP/1 граница тела запроса задаётся двумя способами: `Content-Length` и `Transfer-Encoding: chunked`. Если фронт и бэкенд понимают их по-разному — один запрос превращается в два. Классика десинка.

## Почему HTTP/2 — и как всё равно ломается

В H2 каждая часть запроса идёт с явной длиной, ambiguity убрана на уровне протокола. Но: фронт-прокси принимает H2, а бэкенду пересылает H1 (даунгрейд). При переводе фронт собирает HTTP/1.1-запрос сам, и вот тут начинается магия.

Ключевой трюк: H2-запрос несёт `Content-Length` «для совместимости». Ставим `Content-Length: 0`, а в тело кладём полноценный HTTP/1-запрос:

```
POST / HTTP/2
content-length: 0

GET /admin HTTP/1.1
Host: localhost
```

Фронт видит пустой POST и закрывает запрос. Бэкенд по H1 читает: тела нет (CL 0), дальше в потоке — новый запрос. Смаггленный `/admin` уходит к бэкенду, хотя фронт его никогда не видел.

## h2c

Вторая вектор — HTTP/2 cleartext. Отправляем `Upgrade: h2c`, фронт поднимает H2-туннель до бэкенда, и последующие запросы идут по нему мимо фронтовой логики.

## Заметка

Само по себе — не баг HTTP/2, а баг границы протоколов. Вывод для тестов: если видишь H2 перед проксей — всегда проверяй, что происходит после даунгрейда. Burp это умеет из коробки, ловится быстро, бьётся неприятно.
