# Обход 2FA перебором: макрос для повторного входа

**Лаба:** [2FA bypass using a brute-force attack](https://portswigger.net/web-security/authentication/multi-factor/lab-2fa-bypass-using-a-brute-force-attack) (Expert, Authentication)
**Суть:** после двух неверных четырёхзначных кодов приложение завершает сессию. Макрос автоматически повторяет вход перед каждой попыткой, поэтому эта защита не останавливает перебор.

## Проблема

Учётные данные carlos:montoya известны. У четырёхзначного кода 10 000 вариантов, но после двух ошибок приложение завершает сессию и прерывает перебор.

## Решение: session handling rule + macro

Перед каждой попыткой в Intruder настраиваем повторный вход через макрос Burp:

1. **Sessions → Session handling rules → Add**, область действия — все URL.
2. **Rule Action → Run a macro**, записываем макрос из трёх запросов:
   ```
   GET  /login
   POST /login          (carlos:montoya)
   GET  /login2
   ```
3. Test macro — последний ответ должен быть страницей с запросом кода. При применении правила к Intruder макрос повторяет вход перед каждой попыткой. Счётчик ошибок в отдельной сессии не достигает порога завершения.

## Перебор

`POST /login2` в Intruder, позиция на `mfa-code`, Numbers 0–9999, step 1, min/max digits 4 (чтобы `0007`, а не `7`). **Resource pool: maximum concurrent requests = 1** — иначе параллельные запросы могут использовать сессии, обновлённые другими запусками макроса. Ответ 302 указывает на принятый код. Через «Show response in browser» открываем сессию carlos.

## Как обнаружить

В журналах стоит искать частые повторные входы и сотни POST на `/login2` для одной учётной записи. Ограничение попыток нужно привязывать к учётной записи, а не только к сессии: повторный вход не должен сбрасывать счётчик неверных кодов.

## Заметка

Завершение сессии не заменяет ограничение попыток: автоматический повторный вход позволяет продолжить перебор. Более длинный код увеличит число вариантов, но без ограничений частоты и общего числа попыток этого недостаточно.
