# SSRF: обход фильтра со списком разрешённых хостов

**Лаба:** [SSRF with whitelist-based input filter](https://portswigger.net/web-security/ssrf/lab-ssrf-with-whitelist-filter) (Expert, SSRF)
**Суть:** фильтр проверяет хост по списку разрешённых, но проверка и отправка запроса используют разные правила разбора URL.

## Логика защиты

`stockApi` принимает только URL с хостом `stock.weliketoshop.net`. Попытка `http://127.0.0.1/` отклоняется с «External stock check host must be stock.weliketoshop.net». Для обхода проверяем, одинаково ли фильтр и HTTP-клиент разбирают адрес.

## Обход

В URL данные пользователя могут стоять перед `@`: `http://[email protected]/`. Проверяем: `http://username@stock.weliketoshop.net/` — принято, значит валидатор читает хост после `@`.

Символ `#` обозначает начало фрагмента URL, который не отправляется серверу. Фильтр отклоняет буквальный `#`, но пропускает его при двойном URL-кодировании:

```
stockApi=http://localhost:80%2523@stock.weliketoshop.net/admin/delete?username=carlos
```

При проверке `%2523` ещё не превратился в `#`, поэтому валидатор видит разрешённый хост `stock.weliketoshop.net`. После дополнительного декодирования HTTP-клиент разбирает адрес иначе: `http://localhost:80#@stock.weliketoshop.net/...`. Часть с `@` попадает во фрагмент, хостом становится `localhost`, а портом — `80`. В лабораторной цель — запрос к административному интерфейсу, но приведённая здесь схема URL этого ещё не доказывает: путь после `#` тоже становится частью фрагмента. Полный запрос и порядок декодирования в этой заметке требуют сверки с лабораторной.

Примеры выше сохранены из исходной записи. Строка с `[email protected]` выглядит повреждённой; использовать её как готовый URL нельзя.

## Заметка

Проверка хоста не помогает, если после неё URL декодируется и разбирается иначе. Проверять нужно тот адрес, к которому HTTP-клиент действительно установит соединение.
