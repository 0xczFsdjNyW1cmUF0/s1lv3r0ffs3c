# GhostBusters: две CVE в Ghost CMS и служба выдачи флагов

**Таск:** GhostBusters (aclabs.pro, сезон 7, простой, 2 флага)
**Источник:** [разбор seobuster на Хабре](https://habr.com/ru/articles/1076134). Ниже — конспект этого прохождения.
**Цепочка:** SQLi в Content API → подбор пароля по bcrypt-хэшу → админка → RCE через тему → эксплуатация уязвимости ядра → действия, запускающие выдачу флагов.

## Первоначальный доступ

Открыты порты 22 и 80, веб-сервер — nginx. Сайт перенаправляет на `ghostbusters.acl`; имя добавляется в `/etc/hosts`. Версия Ghost CMS 6.19 видна в исходном коде страницы. В разборе используются две уязвимости:

1. **CVE-2026-26980** — SQLi в Content API без аутентификации. Позволяет получить email и bcrypt-хэш пароля. После подбора пароля через John the Ripper доступна админка `/ghost/#/signin`.
2. **CVE-2026-29053** — RCE через загрузку темы с правами администратора. После загрузки и активации темы страница со слагом `/rce` запускает код. Полученная оболочка работает от пользователя slimer и требует настройки терминала.

Для настройки интерактивной оболочки используются `pty.spawn`, `stty raw -echo; fg` и переменная `TERM`.

## Root и выдача флагов

На ядре Debian 6.12 автор использует dirtyfrag и получает root, но самих флагов в файловой системе ещё нет. В `/root/letter_for_you.txt` есть указание сменить пароль root. linpeas также выделяет `secservice.service`, работающую от root.

В бинарнике `/usr/local/bin/secservice` сохранены символы. В Ghidra видны две проверки с интервалом 15 секунд:

- Первая вызывает `lstat` для `/home/slimer/.slimer/slimer.png` и проверяет, что это обычный файл (S_IFREG). После удаления или переименования вызывается `create_user_report()` и появляется user-флаг.
- Вторая проверяет изменение хэша пароля root относительно значения при запуске службы. После `sudo passwd` root-флаг появляется в `/root/final_report.txt`.

Получения root здесь недостаточно: служба выдаёт флаги только после предусмотренных автором машины действий.

## Как обнаружить

Для расследования SQLi полезны журналы запросов к `/ghost/api`, ошибки приложения и БД, если они записываются. Сама по себе частота запросов не доказывает SQLi. Неожиданную загрузку темы можно искать в журнале действий администратора и HTTP-запросах к админке. Эксплуатация ядра не обязана оставлять запись в обычных журналах; для её обнаружения может понадобиться телеметрия EDR или системного аудита. `secservice` в этой задаче — механизм выдачи флагов, а не средство обнаружения атак.

## Заметка

Версия CMS из исходного кода помогает сузить поиск известных уязвимостей. После получения root имеет смысл прочитать подсказки и проверить нестандартные службы: на этой машине именно служба определяет, когда появятся флаги.
